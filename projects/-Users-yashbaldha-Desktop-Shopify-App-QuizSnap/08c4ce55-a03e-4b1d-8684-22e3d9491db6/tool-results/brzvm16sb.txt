## A/B Test Architecture

### What Can Be Tested
- Quiz title and description
- Question order and wording
- Question types (e.g., image choice vs text choice)
- Number of questions (short quiz vs long quiz)
- Result page layout and copy
- Widget display mode (popup vs inline vs slide-in)
- Popup trigger timing
- Call-to-action button text and color
- Product recommendation count

### Traffic Split Model
- Uses the ABTest model: variantA (original), variantB (variation)
- Split percentage configurable (default: 50/50)
- Assignment is sticky per visitor (cookie-based)
- Cookie name: `qs_ab_{testId}`
- Cookie lifetime: 30 days

## Process

### Step 1: Define the Test
- Parse $ARGUMENTS for what element to test
- Identify the hypothesis (what change should improve what metric)
- Define the primary metric (completion rate, conversion rate, etc.)
- Define secondary metrics (engagement, time on quiz, etc.)
- Calculate minimum sample size for statistical significance

### Step 2: Configure Variants
- Create the ABTest record in the database
- Set up variant A (control — current version)
- Set up variant B (treatment — the change)
- Configure the traffic split percentage
- Set the test status to "draft"

### Step 3: Implement Traffic Splitting
- On widget load, check for existing AB test cookie
- If no cookie, assign variant based on split percentage
- Set cookie with variant assignment
- Load the correct quiz variant based on assignment
- Ensure consistent experience across page loads

### Step 4: Implement Metric Tracking
- Tag all analytics events with the variant identifier
- Track per-variant:
  - Quiz views (impressions)
  - Quiz starts
  - Quiz completions
  - Product clicks
  - Add to cart events
  - Completion rate (completions / starts)
  - Conversion rate (add_to_cart / completions)
- Store variant info in AnalyticsEvent metadata

### Step 5: Build Test Dashboard
- Show test status (draft, running, completed)
- Display per-variant metrics side by side
- Show statistical significance indicator
- Show confidence level (aim for 95%)
- Display estimated time to reach significance
- Add controls: start test, pause test, declare winner

### Step 6: Monitor and Analyze
- Check results daily (or on-demand)
- Calculate statistical significance using chi-squared test
- Flag if one variant is significantly underperforming (safety check)
- Auto-pause if variant B conversion drops below threshold

### Step 7: Declare Winner
- When statistical significance (95% confidence) is reached:
  - Highlight the winning variant
  - Show improvement percentage
  - Offer one-click "apply winner" to make it permanent
- If no significant difference after sufficient sample:
  - Recommend ending the test
  - Suggest a different element to test

## Statistical Method
- Test type: Two-proportion z-test
- Minimum confidence level: 95% (p < 0.05)
- Minimum sample size per variant: 100 conversions
- Recommended runtime: at least 7 days (captures weekly patterns)

## Process

### Step 1: Design the API Contract
- Define the HTTP method (GET, POST, PUT, DELETE)
- Define the route path following Remix conventions
- Design the request body / query parameters schema
- Design the response shape with proper status codes
- Document error response format

### Step 2: Choose the Route Type
- **Admin route** (`app/routes/app.*.tsx`): Protected by Shopify admin auth
- **API route** (`app/routes/api.*.tsx`): For programmatic access
- **Public route** (`app/routes/public.*.tsx`): For storefront widget calls
- **Webhook route** (`app/routes/webhooks.*.tsx`): For Shopify webhook handlers

### Step 3: Implement the Endpoint

For admin routes:
- Use `authenticate.admin(request)` in loader/action
- Access shop via session: `const { admin, session } = await authenticate.admin(request)`
- Return JSON with proper typing

For public/storefront routes:
- Add CORS headers (Access-Control-Allow-Origin with allowlist)
- Validate the request origin or use app proxy authentication
- Rate limit considerations for public endpoints
- Never expose sensitive shop data

For webhook routes:
- Verify HMAC signature via `authenticate.webhook(request)`
- Process asynchronously if heavy work is needed
- Return 200 immediately to avoid Shopify timeout
- Handle idempotency (webhooks can be sent multiple times)

### Step 4: Add Validation
- Validate all input parameters (type, format, required fields)
- Use Zod or manual validation for request body parsing
- Return 400 with descriptive error messages for invalid input
- Sanitize string inputs before database operations

### Step 5: Implement Business Logic
- Keep route files thin — extract logic to service files if complex
- Use Prisma transactions for multi-step operations
- Always scope database queries by shopId
- Handle edge cases (not found, duplicate, unauthorized)

### Step 6: Add Response Headers
- Set `Content-Type: application/json` for JSON responses
- Add CORS headers for public endpoints
- Add cache headers where appropriate

### Step 7: Test the Endpoint
- Test happy path with valid input
- Test with missing required fields
- Test with invalid data types
- Test unauthorized access (wrong shop, no session)
- Test CORS preflight (OPTIONS request) for public endpoints

## Process: Schema Changes

1. Read current `prisma/schema.prisma` to understand existing models
2. Plan the change — add model, add field, modify field, add relation
3. Apply the change to schema.prisma
4. Run `npx prisma validate` to check syntax
5. Run `npx prisma db push` to apply to dev database
6. Run `npx prisma generate` to update the Prisma client
7. Update any TypeScript types that reference the changed models

## Process: Query Optimization

1. Identify the slow query (check loader/action files)
2. Analyze the query — look for N+1 problems, missing includes, large selects
3. Add proper `select` clauses to fetch only needed fields
4. Add `include` for required relations instead of separate queries
5. Add database indexes in schema.prisma if needed (`@@index`)
6. Use `findMany` with `take`/`skip` for pagination
7. Consider caching for frequently-read, rarely-changed data

## Process: Data Operations

1. Identify the operation scope (single shop, all shops, specific records)
2. ALWAYS include `shopId` in WHERE clauses — never operate across shops
3. Use Prisma transactions for multi-step operations
4. Validate input data before writing to the database
5. Handle unique constraint violations gracefully

## Caution Rules

- NEVER delete data without explicit confirmation — soft delete preferred
- NEVER run raw SQL unless Prisma cannot express the query
- ALWAYS back up before destructive schema changes in production
- ALWAYS scope queries by shopId to maintain data isolation
- NEVER store sensitive data (API keys, tokens) in plain text — use encryption
- NEVER modify the Session model — it is managed by Shopify's auth system
- ALWAYS use transactions when updating multiple related records
