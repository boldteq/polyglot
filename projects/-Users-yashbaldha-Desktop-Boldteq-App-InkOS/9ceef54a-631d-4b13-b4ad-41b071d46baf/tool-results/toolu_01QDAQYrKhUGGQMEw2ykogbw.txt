## 5. Dual-Stack Payment Architecture

### 5.1 — L1 (Dodo, current, do not refactor)

| Concern | Implementation |
|---------|----------------|
| Client | `lib/dodo/client.ts` (lazy-init Proxy singleton, never construct at module-eval) |
| Webhook | `app/api/webhooks/dodo/route.ts` — `standardwebhooks` spec, `timingSafeEqual` HMAC |
| Subscription lifecycle | `subscription.active|cancelled|failed|renewed`, `payment.succeeded|failed` — webhook-only writes via service-role |
| Customer portal | `lib/dodo/portal.ts` returns `{ link }` (NOT `{ url }`) |
| Tax | Dodo handles globally (MoR) — receipts branded as Dodo |

### 5.2 — L2 (Stripe Connect Express, NEW)

**Connected account model: ONE Express account per studio + optional second Express account per artist who opts into direct payouts.** This avoids the W-2 pseudo-employer trap (IRS ABC test) and mirrors Vagaro/Mindbody mechanics.

**Studio onboarding flow:**
1. Owner clicks "Enable in-studio payments" in `/settings/payments`.
2. Server creates Express account: `stripe.accounts.create({ type: 'express', country, capabilities: { card_payments, transfers, tax_reporting_us_1099_nec } })`.
3. Server stores `stripe_connected_accounts` row, returns `account_links.create()` URL → studio redirects to Stripe-hosted KYC.
4. Webhook `account.updated` flips `onboarding_status` → `active` when `charges_enabled` and `payouts_enabled` are true.
5. Until KYC complete, Bone/Onyx-tinted banner on `/dashboard`.

**Artist onboarding flow:** Same shape, separate account per artist. Until artist completes KYC, their commission accrues to studio's connected balance and the studio pays them via existing payroll (1099 or W-2 path).

**Charge flow (destination charge model):**
```ts
stripe.paymentIntents.create({
  amount: total_cents,                         // base + tip + tax
  currency: 'usd',
  customer: client_stripe_customer_id,
  payment_method: pm_id,
  confirm: true,
  application_fee_amount: studio_commission_cents,  // 30% in 70/30
  transfer_data: { destination: artist_connected_account_id },
  on_behalf_of: artist_connected_account_id,
  automatic_tax: { enabled: true },            // Stripe Tax for US per-state
  metadata: {
    studio_id, artist_id, booking_id, project_id, session_id,
    deposit_pool_drawdown_cents,
    inkos_idempotency_key                      // dedupe in webhook reconciliation
  }
})
```

**Deposit pool atomic settlement:**
- `projects.deposit_pool_cents_available` = source of truth.
- RPC `apply_deposit_to_session(project_id, session_id, draw_cents)` runs in single transaction:
  1. Verify `available >= draw_cents`.
  2. Decrement `available`, increment `applied`, insert `project_deposit_transactions` row with `kind='applied'`.
  3. PaymentIntent `amount` = `(session_total - draw_cents)` — only balance is charged.
  4. SAGA pattern: deposit txn flagged `pending_apply`, flips to `applied` only on `payment_intent.succeeded` webhook.
- Deposit-only charges (collected at booking creation) hit studio's connected balance with NO `transfer_data` — sit in studio float until applied.

**Tip routing:** Tips captured in same PaymentIntent as session charge (line `tip_amount_cents`). `application_fee_amount` excludes tip → 100% of tip flows to artist's `transfer_data.destination`. Studios that pool tips can override → tip goes to studio account, daily transfer cron splits per pool rule.

**Tax line items:** `automatic_tax: { enabled: true }` enables Stripe Tax. Covers all US states + most EU/CA/AU. For uncovered jurisdictions (rural EU regions, tribal-land tattoo taxes), fallback to `tax_rates: [tx_id]` populated manually per location in `/settings/tax`. Tax amount recorded on charge metadata AND in `tax_remittance_ledger` for monthly remittance.

**Per-state US tattoo-service tax matrix:** NYC 4.5% local + 8.875% retail · NJ 6.625% services · CA/TX/FL/PA/GA exempt for services · IA/MA tax permanent makeup · UK 20% VAT above £90k · CA 5–15% GST/HST/PST · AU 10% GST above AU$75k.

**Refund flow:**
```ts
stripe.refunds.create({
  payment_intent,
  amount,
  reverse_transfer: true,            // claws artist's share back
  refund_application_fee: true       // returns studio's commission
})
```
Mirror by inserting `commission_splits` row with `kind='reversal'` and re-incrementing `deposit_pool_cents_available` if pool-originated.

**Dispute flow:**
1. Webhook `charge.dispute.created` → insert `stripe_disputes`.
2. Enqueue BullMQ job `assemble-dispute-defense-pack`.
3. Job pulls signed consent + photo release + all session photos + chat history snapshot + deposit policy text + receipt → bundles into one PDF, uploads to private Storage.
4. Submit evidence via `stripe.disputes.update()` 24h before `evidence_due_by`.
5. If lost: Stripe debits studio's balance; mirror via `commission_splits` reversal clawing artist share, OR if artist balance negative, log to `payroll` for next-cycle deduction.

**1099-NEC export:** Annual cron at year-end queries `stripe.transfers.list` per artist's connected account, groups by tax year, exports CSV with `name, TIN/SSN/EIN, federal_id, state_id, total_paid, address` to `/admin/tax-exports`. For studios on studio-pool model (artist no own connected account), 1099-NEC generated from `commission_splits` table directly. Stripe also offers `tax_reporting_us_1099_nec` capability — enable on every connected account and cross-check.

### 5.3 — Webhook reconciliation (both rails)

```sql
CREATE TABLE webhook_events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  source TEXT NOT NULL CHECK (source IN ('dodo', 'stripe')),
  event_id TEXT NOT NULL,
  event_type TEXT NOT NULL,
  payload JSONB NOT NULL,
  signature_verified BOOL NOT NULL,
  processed_at TIMESTAMPTZ,
  error TEXT,
  retry_count INT DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE (source, event_id)
);
```

- `INSERT ... ON CONFLICT (source, event_id) DO NOTHING` is first write of every webhook handler — replay returns 200 immediately.
- Reject events older than 5 minutes (timestamp header check).
- Hourly reconciliation cron: list active Dodo subs vs `subscriptions` table; list Stripe charges in last 25h vs `stripe_charges` — flag drift to `/admin/payments/reconciliation`.
- `BullMQ` queue `webhook-replay` per source, 3× retry exponential (30s, 5m, 1h), then dead-letter for manual.

### 5.4 — Failure modes

| Mode | Detection | Handling |
|------|-----------|----------|
| `restricted_soon` | `account.updated` webhook | Onyx banner on dashboard, link to KYC. Charges still work. |
| Cross-border FX | `presentment_currency` ≠ `settlement_currency` | Record both `amount_cents` (settled) and `presentment_amount_cents`. |
| Dispute lost | `charge.dispute.closed` `status=lost` | `commission_splits` reversal; if artist balance negative, log to payroll deduction. |
| Refund after payout | `requires_action` for transfer reversal | Always pass `reverse_transfer: true`. |
| Tax remittance failure | Stripe Tax API error | Don't block charge; queue ledger row `status=manual_review`. |
| Webhook signature mismatch | `timingSafeEqual` fails | Log to `audit_log`, return 401, alert via Hawk. |

## 9. Sequencing Logic

**Why epics are ordered this way:**

1. **Epic 1 (Stripe Connect) first** — every later money-touching feature (deposit pool in portal S34, flash deposit-gate S49, lifecycle credits S43, multi-currency S67, apprentice splits S73, dispute packs S86) depends on Connect rail. Building any earlier means rework.
2. **Epic 2 (AI Assist) before Epic 3 (Client Safety)** — inbound-reply-draft job lives in inbox UI that Epic 2 also rebuilds. Building portal first forces second pass on inbox.
3. **Epic 3 (Allergies + Portal + Briefing + Financial)** — closes Tier 1 launch-blocker chain. Critical path ends at S37.
4. **Epic 4 (Sessions table promotion)** runs after launch-critical because it's a data-shape migration. Earlier risks losing Tier 1 velocity.
5. **Epic 5 (Public surface)** depends on portal foundation (S33) and brand pass (S38). Unblocks Enterprise custom domain (S47 → S60+).
6. **Epic 6 (Compliance/Tax/Analytics)** depends on payments + sessions. Tax sub-ledger needs Connect. REACH fail-fast needs sessions table.
7. **Epic 7 (Enterprise)** depends on multi-location data shapes from Epic 6 (#57).
8. **Epic 8 (i18n + multi-currency)** intentionally after Enterprise — cross-border Connect needs Connect at maturity.
9. **Epic 9 (Workforce + Onboarding)** depends on every prior epic — onboarding wizard touches Connect, brand, license, BBP, tax.
10. **Epic 10 (Hardening)** is penultimate — can't harden until features complete. Earlier = re-hardening every sprint.
11. **Epic 11 (Brand/Demo/PDF/DR)** is final polish layer. Demo personas must reflect *finished* product.

**What can run in parallel:**
- S13 (schema) ‖ S14 (webhook wiring) once Dato finalizes RPC signatures.
- S19 (Stripe Tax) ‖ S14–S18 — tax matrix is independent of charge flow.
- S26 (consult summary) ‖ S25 (reply drafts) — independent AI jobs.
- S39 (sessions table) ‖ S40 (photo slots) only if Dato writes both migrations cleanly.
- S46 (subdomain) ‖ S48 (kiosk) — different surfaces.
- S60 (white-label) ‖ S61–S63 (API) — can fan out.
- S68 (i18n) ‖ S69 (fr/de copy) once locale shells exist.

**Hard dependency edges:**
- S13 → everything in Epic 1
- S22 (refactor gate) → Epic 2 start
- S37 → Epic 4 start
- S39 → S40 → S41 → S42 → S43 → S44 (lifecycle is sequential)
- S65 (feature-key wiring) → Epic 7 launchable

## 10. Quality Gates — Every Sprint

Run in same order, every sprint, no exceptions. **If any gate fails, sprint is NOT closed. No "fix in next sprint" — fix in *this* sprint or extend.**

1. **`pnpm typecheck`** — zero errors.
2. **`pnpm build`** — zero warnings.
3. **Sage diff audit** — zero CRITICAL findings; HIGH findings logged with explicit defer rationale.
4. **Luna test pass** — new tests for new code (unit + integration where applicable + Playwright for any new public flow).
5. **Demo seed regenerated and verified** — `pnpm db:seed:demo:reset && pnpm db:seed:demo:verify` exits 0; new feature visible on demo studio.
6. **`inkos-lessons.md` updated** — any new lesson surfaced (RPC mismatch, drift, gotcha) appended with sprint reference.

### Refactor sprints (10 total: S22, S31, S37, S45, S52, S59, S66, S71, S77, S83)

Every 5–7 feature sprints. Each refactor sprint:
- Type checker zero-warnings audit + `pnpm db:types` regenerated
- Lighthouse performance audit (every changed route, LCP <2.5s, CLS <0.1, INP <200ms)
- Sage full-codebase review in diff mode against last refactor checkpoint
- Lesson extraction via `/train` against last 5–7 sprints, updates `inkos-lessons.md`
- Migration squash check — no orphans, no skipped numbers, all RPCs have shared TS interfaces, types regenerated
